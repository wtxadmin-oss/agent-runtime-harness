## 一、物理目录结构

```
nanobot/                        ← 项目根
├── nanobot/                    ← 后端核心（Python 包，pip install -e .）
│   ├── cli/                    ← 三种启动模式入口（gateway / agent / serve）
│   ├── api/                    ← OpenAI 兼容 HTTP 服务（serve 模式）
│   ├── channels/               ← 12 种平台接入（websocket/telegram/feishu/...）
│   ├── bus/                    ← 消息总线，解耦 Channel 与 Agent
│   ├── agent/                  ← AgentLoop、记忆、上下文、子 Agent
│   │   └── tools/              ← LLM 可调用工具（文件/shell/web/MCP/...）
│   ├── session/                ← 多会话状态管理（按 channel:chat_id 隔离）
│   ├── command/                ← 内置斜杠命令路由（/help /new 等）
│   ├── skills/                 ← 可插拔技能包（9 个）
│   ├── providers/              ← LLM 后端适配（DeepSeek/Claude/GPT/...）
│   ├── cron/                   ← 定时任务调度
│   ├── heartbeat/              ← 定期心跳（保活 + 记忆整理）
│   ├── config/                 ← 配置加载、Schema、路径管理
│   ├── security/               ← SSRF/沙箱/网络安全策略
│   └── utils/                  ← 工具函数库
├── webui/                      ← 前端（React + Vite + TypeScript + TailwindCSS）
├── bridge/                     ← WhatsApp 桥接（Node.js 独立进程）
├── docs/                       ← 文档目录
└── tests/                      ← 测试套件
```

## 三、三种启动模式对比

| 命令 | 消息入口 | 走 Bus | 典型用途 |
|------|---------|--------|---------|
| `nanobot gateway` | Channel（websocket/telegram/feishu 等） | ✅ | 生产部署，多平台接入 |
| `nanobot agent` | 终端 stdin | ❌ | 本地开发调试，交互式对话 |
| `nanobot serve` | HTTP `/v1/chat/completions` | ❌ | API 服务，OpenAI SDK 兼容 |

## 四、核心消息链路（gateway 模式）

```
用户发消息
    │
    ▼
Channel（如 FeishuChannel）
    │  收到 WebSocket 事件，解析消息内容
    │  调用 _handle_message()
    ▼
bus/queue.py（MessageBus.inbound 队列）
    │  InboundMessage 入队
    ▼
agent/loop.py（AgentLoop.process()）
    │  从队列消费消息
    │  查找/创建 Session（按 channel:chat_id）
    │  构建上下文（历史消息 + 系统提示词 + 技能）
    ▼
providers/（LLM API 调用）
    │  流式返回 token delta
    ▼
agent/tools/（工具调用循环）
    │  文件读写 / shell exec / web fetch / cron 等
    │  最多 max_tool_iterations 轮
    ▼
bus/queue.py（MessageBus.outbound 队列）
    │  OutboundMessage 出队
    ▼
ChannelManager._dispatch_outbound()
    │  Delta 合并优化（减少 API 调用次数）
    ▼
Channel.send() / Channel.send_delta()
    │  发回用户（流式卡片 / 普通消息）
    ▼
用户收到回复
```

**旁路说明**：Cron 和 Heartbeat 绕过 Bus，直接调用 `agent.process_direct()`，适合主动触发型任务。

## 五、Session 与 Memory 机制

### 配置文件位置

主配置文件：`~/.nanobot/config.json`（JSON 格式，camelCase）

### 环境变量插值

配置文件中可使用 `${VAR_NAME}` 引用环境变量，例如：
```json
{
  "channels": {
    "feishu": {
      "appId": "${FEISHU_APP_ID}",
      "appSecret": "${FEISHU_APP_SECRET}"
    }
  }
}
```

### .env 自动加载顺序

启动时 `config/loader.py` 按顺序尝试加载（非覆盖模式，先加载的优先）：
1. `~/.nanobot/.env`（配置目录）
2. `./` 当前工作目录 `.env`
3. `~/.nanobot/.env`（同上）

## 八、项目启动步骤

### 8.1 首次初始化（仅需一次）

```bash
# 权限修复（如遇权限问题）
sudo chown -R vscode:vscode ~/.nanobot/

# 初始化工作目录与配置
nanobot onboard
```

编辑 `~/.nanobot/config.json`，设置 provider 与 model：
```json
{
  "providers": {
    "deepseek": {
      "apiKey": "${DEEPSEEK_API_KEY}"
    }
  },
  "agents": {
    "defaults": {
      "provider": "deepseek",
      "model": "deepseek-v4-flash"
    }
  }
}
```

### 8.3 启动 Gateway（后端）

```bash
# 方式一：source 项目 .env 后启动（临时）
set -a && source /workspaces/nanobot/.env && set +a
nanobot gateway

# 方式二：直接启动（推荐，~/.nanobot/.env 会自动加载）
nanobot gateway
```

### 8.4 启动 WebUI 前端（开发模式）

```bash
cd /workspaces/nanobot/webui
bun run dev
```

访问：http://localhost:5173

### 8.5 CLI 交互模式（本地调试）

```bash
nanobot agent
```

## 九、飞书 Channel 持久化配置

### 配置现状

`~/.nanobot/config.json` 中飞书配置已启用，使用环境变量引用：

```json
{
  "channels": {
    "feishu": {
      "enabled": true,
      "appId": "${FEISHU_APP_ID}",
      "appSecret": "${FEISHU_APP_SECRET}",
      "encryptKey": "",
      "verificationToken": "",
      "allowFrom": ["*"],
      "reactEmoji": "THUMBSUP",
      "groupPolicy": "mention",
      "streaming": true,
      "domain": "feishu"
    }
  }
}
```

### 持久化方案

**环境变量已写入 `~/.nanobot/.env`**，此文件在每次 `nanobot gateway` 启动时自动被加载，无需手动 `source`：

```
~/.nanobot/.env 内容：
FEISHU_APP_ID=cli_a965c6a310b85cd1
FEISHU_APP_SECRET=sUGJv0g1evKoRTvQeULaVgVumywvLE7O
DEEPSEEK_API_KEY=sk-67961a0c24064029a248ae9640a07f3b
```

### 自动加载原理

```python
# nanobot/config/loader.py → _load_dotenv_files()
candidates = [
    cfg_dir / ".env",        # ~/.nanobot/.env ← 飞书凭证存于此处
    Path.cwd() / ".env",
    Path.home() / ".nanobot" / ".env",
]
```

加载采用 `os.environ.setdefault`（非覆盖），即环境中已有的变量不会被覆盖。

### 飞书 Channel 连接方式

飞书使用 **WebSocket 长连接**（无需公网 IP / 反向代理）：
- 自动重连，断线后 5 秒重试
- 在独立线程运行 `lark.ws.Client`，通过 `asyncio.run_coroutine_threadsafe` 与主 asyncio 循环通信
- 消息去重（缓存最近 1000 条 message_id）
- 支持 CardKit 流式输出（打字机效果）
- 支持图片/文件/音频上传与下载

## 十一、用户自定义 LLM 与思考模式

### 11.1 架构概览

nanobot 支持两条模型链路并行：

```
全局基座模型（basellm）           用户自定义模型
  config.json 全局配置              profile 私有隔离
  providers.<name>.apiKey          workspace/users/<profile>/models.json
  agents.defaults.model/provider   workspace/users/<profile>/.env.models
         │                                  │
         └──────────── AgentLoop 动态路由 ───┘
                       （有 model_id → 用自定义；无 → 回退全局）
```

- **全局基座**：当前配置为 `deepseek-v4-flash`，所有未选择自定义模型的会话均使用。
- **自定义模型**：按 WebUI profile 隔离，不同用户的模型、API Key、会话互不干扰。
- **思考模式**：默认关闭，用户显式开启后才进入启用判断（三条件门槛）。

### 11.2 添加自定义 LLM（WebUI 操作）

在 WebUI 右侧栏通过 `model_add` 协议提交，字段包括：

| 字段 | 必填 | 说明 |
|------|------|------|
| `name` | ✅ | 显示名称，如 `claude-opus-4` |
| `model_name` | ✅ | 实际 API 模型标识，如 `anthropic/claude-opus-4-5` |
| `api_key` | ✅ | API 密钥，**只写入 `.env.models`，不进入 JSON** |
| `base_url` | 可选 | 自定义 API Base URL（默认按 provider 匹配） |
| `supports_thinking` | 可选 | 是否支持思考模式，默认 `false` |
| `thinking_doc_url` | 条件必填 | `supports_thinking=true` 时必须提供 URL 或 snippet 之一 |
| `thinking_snippet` | 条件必填 | 思考参数官方样例代码，与 URL 二选一或同时提供 |

**存储位置**：
```
workspace/users/<profile_id>/
├── models.json        ← 模型元数据（无明文 key）
└── .env.models        ← API Key（env 变量形式）
```

`models.json` 示例：
```json
{
  "models": [
    {
      "id": "uuid-xxx",
      "name": "Claude Opus",
      "model_name": "anthropic/claude-opus-4-5",
      "base_url": null,
      "api_key_env": "MODEL_CLAUDE_OPUS_API_KEY",
      "supports_thinking": true,
      "created_at": "2025-04-27T00:00:00+00:00"
    }
  ]
}
```

`.env.models` 示例：
```
MODEL_CLAUDE_OPUS_API_KEY="sk-ant-xxx"
```

### 11.3 模型选择与动态路由

**WebSocket 协议**：

| 消息类型（入站） | 说明 |
|----------------|------|
| `model_list` | 获取当前 profile 的模型列表 |
| `model_add` | 添加自定义模型 |
| `model_delete` | 删除自定义模型 |
| `model_select` | 选择当前会话使用的模型 |

| 事件类型（出站） | 说明 |
|----------------|------|
| `model_list` | 返回模型列表（key 脱敏） |
| `model_added` | 添加成功，含新模型信息 |
| `model_deleted` | 删除成功 |
| `model_selected` | 选择成功，含 `supports_thinking` 标记 |

**AgentLoop 动态路由逻辑**（`agent/loop.py`）：

```
消息 metadata._model_id 存在
    │
    ├─→ 读取 ModelStore → 找到模型配置
    │       ├─→ 解析 api_key_env / base_url
    │       ├─→ 创建临时 provider 实例
    │       └─→ 本次请求使用临时 provider + model_name
    │
    └─→ 未找到 / 读取失败 → 回退全局 self.runner + self.model
```

会话元数据持久化（跨连接恢复）：
- `selected_model_id`
- `selected_model_name`
- `selected_model_supports_thinking`

### 11.4 思考模式（Thinking Mode）

#### 启用三条件门槛

**必须同时满足以下三条**，才会向 LLM 注入 thinking 参数：

```
1. user_toggle_enabled == true         ← 用户在 UI 主动开启
2. model_supports_thinking == true     ← 模型配置标记为支持
3. global_recipe_exists && validated   ← 全局思考配方已存在且验证通过
```

任一条件不满足 → 走普通流式，不影响正常对话。

#### `reasoning_effort` 参数值

| 值 | 含义 | 适用场景 |
|----|------|---------|
| `"low"` | 低强度思考（budget: 1024 tokens） | 快速响应 |
| `"medium"` | 中强度思考（budget: 4096 tokens） | 默认值 |
| `"high"` | 高强度思考（budget: max(8192, max_tokens)） | 复杂推理 |
| `"adaptive"` | 自适应（模型自决定是否思考） | Claude 专用 |
| `"minimal"` / `"none"` | 关闭思考 | — |

配置位置（全局默认）：
```json
{
  "agents": {
    "defaults": {
      "reasoningEffort": "high"
    }
  }
}
```

#### 各 Provider 思考参数实现

| Provider / Backend | 思考开启时实际发送的参数 |
|-------------------|----------------------|
| **Anthropic** (`anthropic`) | `"thinking": {"type": "enabled", "budget_tokens": N}` |
| **Anthropic adaptive** | `"thinking": {"type": "adaptive"}` |
| **DeepSeek** (`openai_compat`) | `extra_body.thinking.type = "enabled/disabled"` + `output_config.effort` |
| **DashScope/Qwen** | `extra_body.enable_thinking = true/false`，effort 值 `minimum` 映射 `minimal` |
| **Volcengine / BytePlus** | `extra_body.thinking.type = "enabled/disabled"` |
| **MiniMax** (`openai_compat`) | `extra_body.reasoning_split = true/false` |
| **MiniMax** (`minimax_anthropic`) | 使用 Anthropic backend，原生思考参数 |
| **Kimi / Moonshot**（kimi-k2.5/k2.6） | `extra_body.thinking.type = "enabled/disabled"` |
| **OpenAI o1/o3/o4** | `reasoning_effort` 字段，关闭 temperature |
| **Azure OpenAI** | `reasoning.effort` + `include: ["reasoning.encrypted_content"]` |

**注意**：开启 thinking 时自动禁用 `temperature`（除 Anthropic 固定为 1.0）。

#### 思考配方系统（ThinkingRecipe）

为避免对不同模型硬编码 thinking 参数，nanobot 实现了**全局思考配方**机制：

```
存储位置（全局，所有 profile 共享）：
workspace/system/
├── thinking_recipes.json      ← 配方（参数映射）
└── thinking_evidence/         ← 证据快照（URL/snippet 摘要）
    └── <evidence_id>.json
```

**配方工作流**：

```
用户开启思考 → 检查配方是否存在
    │
    ├─→ 存在且有效 → 直接注入参数，开始对话
    │
    └─→ 不存在 → 触发配置流程：
            用户提交 (URL 或 snippet 或两者) → thinking_recipe_submit
                    │
                    ▼
            ThinkingRecipeOrchestrator 编排：
            ├─ 仅 snippet  → code_extractor_subagent
            ├─ 仅 URL      → url_extractor_subagent
            └─ 两者皆有   → 双提取 → 冲突检测 → (冲突时) compare_subagent
                    │
                    ▼
            参数预览 → thinking_recipe_preview（出站事件）
                    │
                    ▼
            用户确认 → thinking_recipe_confirm
                    │
                    ▼
            保存配方 → thinking_recipe_saved
```

**WebSocket 协议**：

| 消息类型（入站） | 说明 |
|----------------|------|
| `thinking_toggle` | 开/关思考，触发配方存在性检查 |
| `thinking_recipe_submit` | 提交 URL 或 snippet（或两者） |
| `thinking_recipe_confirm` | 用户确认预览，触发保存 |

| 事件类型（出站） | 说明 |
|----------------|------|
| `thinking_recipe_required` | 需要配置配方（无可用配方时） |
| `thinking_recipe_progress` | 编排进度（`submitted/extracting/compiling/preview_ready`） |
| `thinking_recipe_conflict_detected` | 检测到 URL/snippet 冲突，含评分信息 |
| `thinking_recipe_preview` | 参数预览（待用户确认） |
| `thinking_recipe_saved` | 配方保存成功 |
| `thinking_recipe_error` | 失败事件 |

**Function Calling 工具**（AgentLoop + SubAgent 均可调用）：

| 工具 | 说明 |
|------|------|
| `thinking_recipe_lookup` | 查询某模型是否已有配方 |
| `thinking_recipe_compile` | 将证据编译为标准参数预览 |

> `save` 操作不开放给 function calling，必须经用户确认后才执行（防止绕过）。

#### 冲突评分维度（双源同时提交时）

当 URL 与 snippet 同时提交且提取结果存在冲突，`compare_subagent` 按以下维度评分：

| 维度 | 说明 |
|------|------|
| 可信度 | 来源权威性 |
| 完整度 | 参数覆盖完整性 |
| 可执行性 | 参数可直接使用程度 |
| 时效性 | 文档/代码的新鲜度 |
| 模型匹配度 | 与目标模型的匹配程度 |

最终决策输出：`url` / `snippet` / `hybrid`（三选一）。

---

### 11.5 全局配置 vs 自定义模型的思考设置

| 设置维度 | 全局基座 | 自定义模型 |
|---------|---------|-----------|
| 配置位置 | `config.json` `agents.defaults.reasoningEffort` | WebUI model_add 时设 `supports_thinking` |
| 配方存储 | `workspace/system/thinking_recipes.json`（全局共享） | 同上，按 `model_name` 索引 |
| API Key 位置 | `~/.nanobot/.env` 或 `config.json` | `workspace/users/<profile>/.env.models` |
| 隔离范围 | 全局，所有 channel | 按 profile，WebUI 会话级 |

## 十二、常见问题

### Q：飞书消息收不到？
- 确认飞书开放平台应用已开启「机器人」能力
- 订阅事件：`im.message.receive_v1`
- 飞书使用 WebSocket，无需配置 webhook 地址

### Q：启动时报 `Environment variable 'FEISHU_APP_ID' not set`？
- 检查 `~/.nanobot/.env` 文件是否存在且格式正确
- 或者在启动前手动：`export FEISHU_APP_ID=xxx`

### Q：如何切换模型？
编辑 `~/.nanobot/config.json` 中的 `agents.defaults.model` 和 `agents.defaults.provider`，或使用 `/config` 命令。

### Q：会话历史在哪里？
`~/.nanobot/workspace/sessions/<channel>:<chat_id>.jsonl`，`/new` 命令清空当前会话。

### Q：如何查看日志？
```bash
nanobot gateway --verbose
```
或查看 `~/.nanobot/logs/` 目录。
